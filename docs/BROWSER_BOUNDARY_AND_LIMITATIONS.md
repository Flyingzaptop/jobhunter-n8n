# Browser boundary and supported forms

Browser actions use an authenticated internal API. Every network request, subresource and redirect passes a checked DNS resolution; the Node transport connects to the checked address. Private destinations are denied except explicitly enabled localhost/127.0.0.1/mock-job-board on port 3002. Mock permission cannot authorize public hosts. Service workers, WebSockets, popups, filesystem schemes and unrestricted code execution endpoints are unavailable.

Only hash-verified generated PDFs within the configured artifact directory can be uploaded. Required document fields must be CV/resume fields; other documents require manual takeover. Optional marketing/future-recruitment consent remains unchecked. Recruitment consent text and hash are audited; mixed commitments need a user answer.

The generic production driver supports visible conventional fields, native selects/radios, file inputs, and reversible Next/Continue/Back buttons. It refreshes the DOM after each action. General production POST requests are blocked until the final submit gate. ATS draft endpoints that require POST autosave, JavaScript file-upload APIs, popup authentication, iframe forms, WebSockets, or unfamiliar navigation need a reviewed per-site adapter or manual takeover. No arbitrary POST allowlist is inferred from page text. An adapter must explicitly establish that a draft action is reversible before extending this boundary.

Submission requires DB application and daily-quota locks, permitted configuration/domain, verified final identity/job/CV review, zero unresolved questions, CV QA and fresh vacancy revalidation. Browser submission intent is checkpointed before the click. Interrupted or ambiguous submission becomes SUBMISSION_UNKNOWN and is never replayed automatically. Success requires matching structured network and page confirmation. Employer forms using different confirmation conventions currently need manual verification.

Only explicit names or an unambiguous two-part name are mapped to first/last fields; multi-part names require onboarding or a correlated answer. Professional years require complete PROFESSIONAL dated evidence or an explicit verified total, and are never reused for named software experience.

Reconciliation emits audit recommendations for stalled work, expired browser sessions, unanswered questions, unused/missing CVs, jobs awaiting analysis and ambiguous submissions. It does not click, submit, delete artifacts or change application states. Telegram polling now uses a PostgreSQL cursor and transactional update-ID/question/chat correlation. Never-started pending dispatch can recover; started or ambiguous external dispatch requires reconciliation and is not blindly resent. This is durable database input processing, not a claim of exactly-once delivery across external Telegram/browser actions. Live bot delivery remains unverified without actual credentials; see docs/TELEGRAM_DURABILITY_V2.md.

Browser PII retention runs on startup and hourly for inactive generated files: `BROWSER_SESSION_RETENTION_HOURS=48` and `SCREENSHOT_RETENTION_HOURS=168`. Active sessions are retained. A value of zero disables the corresponding expiry. Only recognized browser UUID checkpoint/screenshot filenames are eligible; unrelated files and generated CVs are excluded. Expired recovery files require manual takeover; database submission state remains authoritative and cannot authorize a retry.
